# P3 - Approve the Phase A scope (safe data writes)

Decision memo for the owner. Written by Claude Code (Opus 5.5), 2026-10-20. Nothing here is decided; the owner picks.

## The question

`specs/002-phase-a-safety/spec.md` (Codex draft, uncommitted in the home folder) makes every Stranote write locked
and atomic: a named mutex per file plus write-to-temp-then-replace (`Invoke-SnLockedUpdate`, candidate
`phase-a-wip` f30150d, 19 extra tests). It leaves three things **out of scope**. Do you accept these limits?

| # | Out of scope | What can still go wrong | How likely today |
|---|---|---|---|
| 1 | **Explorer edits**: a person editing a JSON file by hand while Stranote writes | Stranote's write replaces the hand edit, or the hand edit replaces Stranote's | Rare; only the owner edits files by hand |
| 2 | **Stale browser saves**: the Settings dialog and the CV page send the whole file | With the dialog open, a change Claude or the menu made in the meantime is overwritten when you press Save | Low, but real when an agent works while the dashboard is open |
| 3 | **Multi-file atomicity**: an operation that writes several files is atomic per file, not as a whole | A crash in the middle leaves some files new and some old | Very low (needs a crash at that exact moment) |

Already in scope and not up for debate: two writers at once never lose an update, task ids never repeat, a broken
JSON file is never replaced with empty data, a failed write leaves the old file intact (FR-001..FR-008).

## The one risk in limit 3 worth knowing

`Approve-SnPackDraft` (`src/StranotePacks.ps1:366`) writes five things in a row: the custom pack file, a backup
`overrides.before-pack-switch.json`, `overrides.json`, `profile.json`, the new folders, then the request status.
If it stops after `profile.json` but before the request is marked `accepted`, the role already uses the new pack
(that part is fine), but the request still says `drafted`. Pressing **Accept** again then **overwrites the backup**
with overrides that were already cleaned, so the person's original overrides are lost. That breaks
"never lose progress" (constitution §IV), and it is the only multi-file path that touches settings.

## Options

**A. Approve the scope as written.**
Cost: none; P4 (forward-port f30150d + T040-T042 writes) can start right after `plan.md` / `tasks.md`.
Risk: the pack-acceptance backup issue above stays until a later phase.

**B. Approve, plus one small addition for pack acceptance (recommended).**
Add one requirement: *re-running an interrupted pack acceptance must finish the job without losing data*: the backup
is written only if it does not exist yet, and the request status is checked against the profile so a second
Accept completes instead of starting over. No general transaction system, no API change.
Cost: about one function plus 2 tests inside P4. Risk: very small; same files, same behaviour on the normal path.

**C. Widen Phase A to also fix stale browser saves (limit 2).**
Needs a version (`rev`) field in `POST /api/settings` and `POST /api/learn/cv`, so the page can be told "this
changed since you opened it". That changes the API contract, which FR-007 forbids for this phase.
Cost: spec rewrite, UI work, new tests; Phase A roughly doubles. Risk: mixes a safety phase with a UI/API change.
Better as its own later phase (it is the `rev` idea in `LOCAL_FIRST_AUDIT.md`, `PHASE_REVIEW.md` U5).

Limit 1 (Explorer edits) has no realistic fix inside the stack; all options keep it as a documented limit.

## Recommendation

**Option B.** It closes the one place where the listed limits can actually lose the person's settings, at a small
cost, and keeps Phase A a pure safety phase. Stale browser saves (C) go on the backlog as a separate phase.
