# D2 - Brand tokens, fonts, and career-neutral defaults

## Decision needed

Approve the recommended direction below, or choose alternatives for the logo accent and font source. The work is split
between Phase H (visual design system) and Phase I (career-agnostic core); this memo does not authorize changing either
phase's scope or starting implementation early.

## Context

`PHASE_REVIEW.md` lists the fixed indigo logo layer, Oracle-red CV export, inconsistent learning-accent fallback,
duplicated inline logo SVGs, Google Fonts CDN request, and EBS-specific category fallback as D2. It maps the visual
items to Phase H and category neutralization to Phase I. The constitution requires career differences to live in
packs, calls for a product accent and a separate learning accent, and describes Stranote as local-first.

The template currently loads fonts from Google, uses a fixed indigo fill in repeated logo SVGs, and falls back to
different colors for the learning accent. `PHASE_REVIEW.md` also notes the existing settings copy says the logo keeps
its indigo top layer; whether that is intentional brand identity or an accent-token gap needs an owner choice.

## Options and recommendation

| Area | Options | Cost and risk | Recommendation |
|---|---|---|---|
| Logo top layer | A. Keep fixed indigo and treat it as a brand token. B. Use the user's app accent. C. Add a separate logo-color setting. | A is smallest and preserves the stated settings behavior, but keeps the logo independent of the selected accent. B is a small token change but makes the mark vary with settings. C adds a setting and support burden. | **A** for now: make the fixed indigo an explicit brand token and keep the explanatory copy. Revisit only if the owner wants the logo to follow the selected accent. |
| CV export color | A. Keep Oracle red. B. Use the generic app accent. | A retains a career-specific visual in the core. B is a small styling change; ensure contrast remains acceptable in exported CVs. | **B**: use the accent token and remove the Oracle-specific color from the generic CV export. |
| Learning-accent fallback | A. Keep the current fallback values. B. Use the documented default `#2563EB` consistently. | A can show a different learning color when a saved value is invalid or absent. B is a small, low-risk consistency fix. | **B**: use the same learning-accent default in validation, rendering, and settings. |
| Repeated logo SVGs | A. Leave three copies and update them together. B. Render them from one shared template/helper. | A is initially cheapest but future token changes can drift. B has a small refactor cost and reduces visual inconsistency risk; verify each rendered surface. | **B**, as part of the Phase H token pass. |
| Font source | A. Keep the Google Fonts CDN. B. Use the system font stack. C. Self-host the font files. | A makes a third-party request on page load, contrary to the local-first/no-telemetry goal. B removes the request with no bundled assets, though glyph metrics may differ by OS. C avoids runtime third-party requests while preserving chosen fonts, but adds assets, licensing review, and maintenance. | **B**: use the system stack now; it is the smallest option and removes the external request. Self-hosting can be reconsidered if typography is a demonstrated product requirement. |
| EBS category fallback | A. Keep EBS categories in the core fallback. B. Keep them in the EBS pack and use one neutral core fallback. C. Remove the fallback. | A violates the career-agnostic boundary. B requires Phase I code/tests and preserves pack-specific behavior. C risks empty or broken category flows for packs without categories. | **B**: move EBS categories to the EBS pack, provide one neutral fallback in the core, and retain the documented pre-migration EBS-pack compatibility path. |

## What this unblocks

- Phase H can implement the visual-token choices without re-deciding whether the logo is allowed to remain indigo,
  which color CV export uses, or how the page obtains fonts.
- Phase I can move EBS category data into its pack while keeping a neutral fallback and legacy migration behavior.
- The recommendation avoids changing user settings or stored data; visual defaults and category sourcing can be
  changed in their respective phases with focused regression tests.

## Owner response

Reply with `D2: approve recommendations` to accept the proposed direction, or identify the area(s) and option(s) to
change. The logo choice is intentionally conservative: the current UI already describes fixed indigo as deliberate.
