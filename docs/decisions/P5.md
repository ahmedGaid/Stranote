# P5 - Phase C change journal vs the "no sync log" anti-goal

Decision memo for the owner. Written by Cline (MiniMax-M3.1-Flash), 2026-10-21. Nothing here is decided; the
owner picks.

## The question

The playbook asks for a change journal in Phase C and forbids a sync log in its anti-goals. Read literally, the
same document requires and forbids the same thing. Which reading wins?

## The two texts

**Playbook §6, Stage 0, Phase C (line 275):**

> **Phase C, change journal**: `changeSeq` + `changes.jsonl` written inside the shared helper, so Claude/menu
> writes are captured; `GET /api/changes?since=<n>`; polling while the tab is visible; start with Questions.
> Optional: `FileSystemWatcher` on `01_Tickets` to capture Explorer edits.

**Playbook §8, anti-goals (line 379):**

> Do not build IndexedDB replication, WebSockets or a sync log for the single-PC product.

**The audit, `LOCAL_FIRST_AUDIT.md` (line 198):** adopting Linear's model would mean "a sync log that must also
capture Claude's and Explorer's writes, and a new runtime surface" - "All of that for one user on one PC, against
the constitution's §IV and §VII."

**The audit's Phase 0 (line 213)** then proposes exactly the Phase C thing: a `changeSeq`, a `changes.jsonl`
(`{seq, entity, id, op, at}`) written inside `Write-LearnList 'questions.json'`, and `GET /api/changes?since=`.

So the audit rejects the *sync log* idea and, in the same document, specifies the *change journal* that Phase C
copies. `PHASE_REVIEW.md` C1 flagged this as "Phase C change journal vs anti-goal" and asked for a reword.

## Why they are not really the same thing

The anti-goal names a thing that has a purpose the product does not need: **moving a copy of the data to another
machine or another user**. IndexedDB replication and WebSockets are the transport for that; a "sync log" is the
record of changes you would replay there.

Phase C's journal has a different purpose: **telling the open tab which entities changed so it refetches them**.
It never leaves the PC, it carries ids rather than a second copy of the truth, and the truth stays in the JSON
files. The audit says this itself, in the line that makes the tripwire explicit (line 224):

> **Only if Stranote becomes multi-device or multi-user** (a spec decision under §VII): revisit the full design.
> At that point the change journal from Phase 0 is already the start of a sync log.

So the audit already treats the change journal as a *possible first step toward* a sync log - never as one.
The ban is on replication; the journal is a refresh aid that happens to be the cheapest way to build the refresh
aid.

Two other playbook lines point the same way:

- §8 line 384: "Do not let agents write through any path that skips locking and **journaling**." The playbook
  already *requires* journaling on every write path. Only "sync log" is forbidden.
- §6 Phase E (lines 287-288): "Patches from writes and from `/api/changes` flow through the same `applyChange()`
  function." Stage 1's client model layer is built on the Phase C feed. Dropping Phase C does not remove the
  journal idea, it removes Stage 1's foundation.

## The dependency worth knowing

Phase C journals "inside the shared helper", i.e. inside `Invoke-SnLockedUpdate` from Phase A (P4). Phase C
therefore waits for Phase A to land. That is the right coupling: the helper is the one place every writer passes
through (browser, terminal menu, Claude skills), so a journal written there catches Claude's writes too - which is
the whole point of the audit's "changes made by Claude only appear after a manual refresh" complaint.

## Options

**A. Drop Phase C, keep the anti-goal as written.**
The dashboard keeps asking the server for everything on refresh; Claude's writes appear only after a manual
refresh. Cost: nothing to build now, but the Stage 1 client model layer (§6 Phase E) loses its patch source and
has to be re-derived later, probably with a worse mechanism. Risk: the anti-goal wins by silence, and the
playbook keeps a contradiction in it that will confuse the next agent (this memo exists because of that).

**B. Reword the anti-goal so it bans replication, not the change feed (recommended).**
Change §8 line 379 to ban only the replication machinery, and add one line saying what a local change feed is
allowed to be. Phase C then runs as written.

Suggested replacement for §8 line 379:

> Do not build IndexedDB replication, WebSockets or a sync log for the single-PC product. A local change feed
> (`changes.jsonl` + `GET /api/changes?since=`) that only tells the open tab which ids changed is not a sync log:
> it never leaves the PC and it keeps no second copy of the truth.

And a line next to Phase C (§6) saying what would turn it into the forbidden thing:

> Phase C stops here on purpose. The moment the feed is used to carry data to another machine or user, it
> becomes the sync log §8 forbids, and that needs its own spec under §VII.

Cost: one line of playbook text plus one sentence in Phase C. Risk: low - it names the tripwire instead of
leaving it to be argued.

**C. Reword the anti-goal and split Phase C further.**
Option B's wording, plus the first slice only: journal **Questions** writes (`Write-LearnList 'questions.json'`),
one entity, no other files, no `FileSystemWatcher` on `01_Tickets`.

Cost: the same text change as B, plus a smaller first phase. Risk: the same as B, and the "start with Questions"
line in Phase C already says this, so C mostly re-states the plan.

## Recommendation

**Option B**, with Option C's scope as the first slice of it (Phase C already says "start with Questions", so
that is a plan detail, not a separate decision).

The reasoning is one line: the anti-goal protects the product from a *replication* runtime it does not need, and
Phase C adds a *local* id feed that keeps no second copy of the truth. Rewording the ban to name the thing it
really bans removes the contradiction, keeps the anti-goal's intent, and leaves Stage 1's foundation in place.

## What approval unblocks

1. Phase C can be planned and built once Phase A (`Invoke-SnLockedUpdate`) has landed - that is P4, which is
   blocked on P3.
2. `PHASE_REVIEW.md` C1 can be closed.
3. Stage 1 (Phase E client model layer) keeps its patch source: one `applyChange()` fed by both writes and
   `/api/changes`.

the fix will be improvised in code rather than written down. This memo does not change anything by itself: the
playbook edit is not made until you pick a letter.
